# Database schema and migrations

The versioned SQL in [`migrations/`](../migrations) is the schema's source of truth.
It matches `domain.Post` and the queries in the PostgreSQL repository. The API does
not create tables or run migrations at startup.

## Data ownership

- **PostgreSQL:** posts, replies, thread relationships, timestamps and reply counts.
- **Redis:** like/dislike membership, feed queues and seen-post sets. There is no
  PostgreSQL reactions table because the current application does not use one.
- **External authentication service:** users. `author_id` is a user UUID, not a
  foreign key to a local table.
- **Goose:** `goose_db_version`, created and managed by the migration library.

## `posts`

| Column | PostgreSQL type | Nullable | Default | Meaning |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | No | — | Primary key; generated by the application |
| `author_id` | `uuid` | No | — | External user ID taken from the JWT |
| `text` | `text` | No | — | Post body; cleared on soft deletion |
| `root_id` | `uuid` | Yes | `NULL` | Original root post of a reply thread; FK to `posts.id` |
| `parent_id` | `uuid` | Yes | `NULL` | Direct parent of a reply; FK to `posts.id` |
| `reply_count` | `bigint` | No | `0` | Number of active **direct** replies |
| `like_count` | `bigint` | No | `0` | PostgreSQL reaction snapshot used by reply ordering |
| `dislike_count` | `bigint` | No | `0` | PostgreSQL reaction snapshot |
| `created_at` | `timestamptz` | No | `now()` | Creation time |
| `updated_at` | `timestamptz` | No | `now()` | Last text edit or soft deletion |
| `deleted_at` | `timestamptz` | Yes | `NULL` | Soft-deletion time; `NULL` means active |

No UUID extension is required. Counts use `bigint` to match Go's `int64`.
The repository supplies creation timestamps explicitly; SQL defaults also allow
manual inserts with fewer columns. There is no automatic `updated_at` trigger:
the repository updates it when editing or deleting a post.

### Threads

For a root post **A**, a reply **B** to A, and a reply **C** to B:

| Post | `parent_id` | `root_id` |
| --- | --- | --- |
| A | `NULL` | `NULL` |
| B | A | A |
| C | B | A |

Both references must be absent or both present. Each references an existing post
and cannot reference the row itself. `ON DELETE RESTRICT` prevents physical removal
of a post referenced by any reply, including a soft-deleted reply.

The handler derives the correct root from the parent. These basic SQL constraints
do **not** verify that `root_id` points to an actual root of the same thread or
prevent multi-row cycles introduced by manual SQL updates. Thread references are
not editable through the current API; manual imports must preserve this invariant.

### Validation and soft deletion

- IDs and author IDs cannot be the zero UUID.
- Counters cannot be negative.
- Text is limited to 10,000 PostgreSQL characters, matching the API's Unicode
  code-point limit for a UTF-8 database. Active text cannot be empty. The API
  additionally rejects whitespace-only input; the database does not duplicate
  Go's Unicode whitespace validation.
- Deletion sets `text = ''`, `deleted_at = now()` and `updated_at = now()`.
  Empty text is therefore allowed when `deleted_at` is set.
- Deleting a root does not delete its replies. Both thread foreign keys survive.
- `reply_count` is incremented/decremented in the repository transaction for the
  **direct parent**, not all ancestors. No SQL trigger duplicates that work.

**Existing application limitations:** like/dislike snapshots are not synchronized
from Redis; the schema does not change that behavior. Also, `DeletePost` currently
requires an active parent when decrementing its counter, so deleting a reply after
its parent was soft-deleted fails and rolls back. This is repository logic, not a
foreign-key restriction; these migrations do not change that workflow.

### Indexes

| Index | Columns / predicate | Purpose |
| --- | --- | --- |
| `posts_pkey` | `id` | Lookup by ID, owner mutations, joins for feed IDs |
| `posts_feed_idx` | `created_at DESC, id DESC`; active rows | Feed candidate ordering; author exclusion remains a filter |
| `posts_replies_idx` | `parent_id, like_count DESC, created_at DESC, id DESC`; active rows | Direct reply filtering, ordering and pagination |
| `posts_parent_id_idx` | `parent_id`; non-null values | Find all direct references during FK checks, including deleted replies |
| `posts_root_id_idx` | `root_id`; non-null values | Find all root references during FK checks, including deleted replies |

## Run migrations

The project embeds SQL migrations in a standalone command using
[Goose](https://github.com/pressly/goose) **v3.28.0** and the existing pgx driver.
It only needs `DATABASE_URL`; Redis, JWKS and HTTP configuration are not required.
An optional `.env` is loaded from the working directory without overwriting
existing environment variables.

Create the PostgreSQL database separately, using UTF-8 encoding, then run from
the repository root:

```sh
go run ./cmd/migrate status
go run ./cmd/migrate up
go run ./cmd/migrate version
go run ./cmd/api
```

`status` reports pending/applied files; `version` prints the highest applied
version (`0` before the initial migration). Goose may initialize its own version
table even for `status` or `version`; these commands do not apply the posts schema.
Running `up` again skips migrations already recorded as applied.

For deployment, build a separate binary with the SQL files embedded:

```sh
go build -o bin/migrate ./cmd/migrate
./bin/migrate -timeout 10m up
```

No migration directory is needed alongside the binary. Rebuild it when adding
migrations. The API binary does not include or invoke the migrator.

Flags go **before** the command. The default operation deadline is five minutes,
including connection and lock acquisition. SIGINT/SIGTERM cancel the operation;
Goose performs connection/lock cleanup afterward. Use a direct PostgreSQL connection
or session-mode pooler: the migration lock is a session-level advisory lock and
must not go through transaction-mode pooling. Concurrent instances of this
migrator use the same Goose lock; unrelated SQL tools do not automatically honor it.

### Migration files

1. `00001_create_posts.sql`: creates `posts`, constraints and database comments.
2. `00002_add_posts_indexes.sql`: adds query and foreign-key indexes.

Each file has `-- +goose Up` and `-- +goose Down` sections and runs in a transaction.
If the second migration fails, the first can remain applied; fix the cause and run
`up` again. The indexes are intentionally normal transactional indexes for initial
schema setup. Future indexes on a large live table may require a separate
`CREATE INDEX CONCURRENTLY` migration with Goose's `NO TRANSACTION` annotation.

### Rollback

```sh
# Rolls back exactly one migration. Review its Down section first.
go run ./cmd/migrate down
```

**Destructive:** from version 2, the first `down` removes only indexes; the next
`down` drops `posts` and all stored posts/replies. Use backups before destructive
schema changes. Normal production evolution should use new forward migrations.

### Existing database

The initial migration targets a fresh schema. It deliberately does not use
`CREATE TABLE IF NOT EXISTS`: an existing incompatible table must not be silently
marked as migrated. If `posts` already contains data, back up the database, compare
its actual schema with these migrations and plan a reviewed baseline/adoption
procedure. Do not drop the table or edit Goose's version history just to bypass
the conflict. No automatic conversion of an existing table is included.

### Add a migration

Create the next file, for example `migrations/00003_add_example.sql`:

```sql
-- +goose Up
-- Forward SQL statements ending with semicolons.

-- +goose Down
-- Reverse SQL statements ending with semicolons.
```

Use unique increasing versions. Never modify an already-applied migration; add a
new file instead. Validate `up`, repeated `up` and `down` against a disposable
database, then rebuild the migrator. Run migrations once as a deployment step
before starting the compatible API version, with a role allowed to perform DDL.

## Integration tests

Unit tests run without external databases. For real PostgreSQL coverage, explicitly
set a **dedicated test database** URL; tests never fall back to `DATABASE_URL`:

```sh
TEST_DATABASE_URL='postgres://postgres:local-password@127.0.0.1:5432/post_service_test?sslmode=disable' \
  go test -race ./internal/adapters/postgresql -run TestMigrationsIntegration -v
```

The test role needs permission to create schemas. Each run creates a random isolated
schema, sets `search_path` to only that schema and drops that exact schema on cleanup.
Tests check migration versions, repeated Up, Down/reapply, indexes, constraints,
repository CRUD, nested replies, counters, rollback of failed reply creation and
feed filtering. Without `TEST_DATABASE_URL`, the integration test is skipped.
